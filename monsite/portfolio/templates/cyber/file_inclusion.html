01

Local vs Remote File Inclusion

File inclusion occurs when an application dynamically loads a resource using a path influenced by a request parameter, route, cookie or stored value.

LFI · Local

Access a local resource

May expose files readable by the application process. The outcome depends on file permissions and the API used.

RFI · Remote

Load a remote resource

Possible when a function and server configuration permit remote URLs. Execution is conditional, not automatic.

Potential impact: source-code disclosure, configuration and secret exposure, filesystem discovery, and in specific conditions server-side code execution.
02

Recognize vulnerable patterns

The root issue is allowing untrusted input to become an arbitrary file path without a safe mapping or effective validation.

PHP · VULNERABLE PATTERN
if (isset($_GET['language'])) {
    include($_GET['language']);
}

Similar patterns can occur in Node.js file-reading APIs, Java/JSP imports, .NET partial rendering, template engines, download routes and avatar handlers. Review direct parameters and values retrieved from a database.

Second-order LFI: a value can be stored first and used in a path later by another feature. Reviewing only the later request may miss the original source.
03

Basic LFI & path traversal

Understand how the application builds the final path. Absolute paths, relative paths, directory prefixes and appended extensions behave differently.

Direct path

Input is passed directly to a file API; the intended directory may not constrain the resource.

Relative traversal

The sequence ../ refers to a parent directory on Unix-like systems. Repeated traversal can escape an intended subdirectory if containment is not enforced.

Prefix / suffix

A fixed directory, filename prefix or extension changes the resolved path and may affect test results.

Verify evidence

Compare a known-good request with a controlled test. A status code alone is not proof; verify the returned content or behavior.

04

Why simple filters fail

Blacklists attempt to recognize dangerous strings instead of enforcing a safe destination.

Non-recursive replacement

A one-pass replacement can leave a traversal sequence in the transformed output.

Encoding & decoding

Proxies, frameworks and application code may normalize input at different stages. Canonicalization must be consistent.

Approved path checks

A prefix-only regular expression can be insufficient if path resolution later escapes that prefix.

Legacy PHP behavior

Null-byte and path-truncation techniques applied to old PHP versions and are obsolete on modern installations.

Defensive takeaway: do not rely on blacklists for traversal sequences, encoded characters or extensions. Enforce a fixed allowlist and verify the canonical resolved path.
05

PHP filters & source disclosure

PHP stream wrappers expose different stream types. In an LFI scenario, a filter may transform file content before the application returns it.

CONCEPTUAL WRAPPER FORMAT
php://filter/read=convert.base64-encode/resource=FILE

Base64 conversion can return PHP source as encoded text instead of rendering the script. In an authorized lab, decode the complete output and review references, configuration access and unsafe file-handling functions.

Read vs execute

A read API may disclose content without executing it. An inclusion or rendering API may interpret the file.

Configuration matters

Wrapper availability depends on settings, extensions, permissions and the vulnerable function.

06

Impact & execution conditions

LFI does not automatically imply remote code execution. The result depends on the inclusion primitive and the server environment.

ScenarioPotential resultDependency
Read local configurationInformation disclosureRead permission
PHP source via filterSource disclosureAccessible resource and wrapper
Remote inclusionRemote content; sometimes executionFunction and configuration
Upload combined with LFIPossible code executionUploaded file can be included and interpreted
Session or log poisoningPossible code executionControlled content and an execution-capable include

Wrappers and optional extensions can increase risk when combined with an inclusion flaw. Their availability must be verified in the lab; never assume a feature is enabled.

07

Uploads, sessions & log poisoning

These techniques share a pattern: user-controlled content is written to a file and later consumed by a vulnerable inclusion function.

File uploads

Store uploads outside executable paths, generate server-side filenames and never include user uploads as templates or scripts.

Session files

Data stored in session files can become dangerous if it is controllable and later included in an execution-capable context.

Server logs

Request headers may be written to logs. Including a log as executable content can turn logged input into a code-execution risk.

Permissions

Separate application code, uploads, logs and secrets. Give the web process only the filesystem access it needs.

08

Automated discovery with ffuf

Fuzzing helps find undocumented parameters and common LFI patterns, but all promising results require manual validation.

AUTHORIZED LAB · PARAMETER DISCOVERY
ffuf -w parameter-names.txt:FUZZ \
  -u 'http://TARGET/index.php?FUZZ=value' \
  -fs RESPONSE_SIZE
AUTHORIZED LAB · LFI WORDLIST TEST
ffuf -w LFI-Jhaddix.txt:FUZZ \
  -u 'http://TARGET/index.php?language=FUZZ' \
  -fs RESPONSE_SIZE

Replace placeholders with values from your own authorized target. Compare response size, content, timing and behavior; an HTTP status code alone is not enough.

Parameters

Check GET and POST fields not visible in the normal interface.

Web root

Identify the document root to understand relative-path resolution.

Configuration

Review permitted server configuration files for document-root and log-path context.

Manual verification

Reproduce findings with the smallest safe test and preserve evidence.

09

Prevention & hardening

The strongest fix is to prevent user input from becoming an arbitrary filesystem path.

  • Map user-facing identifiers to a fixed allowlist of server-side templates or files.
  • Resolve canonical paths and verify they remain inside the permitted directory.
  • Never pass raw request parameters or database values directly into include, render, read or download functions.
  • Store uploads outside executable locations; validate content and generate server-side filenames.
  • Run with least privilege and isolate application code from secrets, logs and unrelated files.
  • Disable remote inclusion features and unnecessary wrappers where possible.
  • Return generic errors to users; keep detailed diagnostics in access-controlled logs.
  • Use a WAF as an extra layer, not as a replacement for secure application code.
SAFER DESIGN · FIXED MAPPING
const pages = {
  en: "pages/en.html",
  es: "pages/es.html"
};
const file = pages[requestedLanguage] ?? pages.en;

HTB Skills Assessment

The supplied scenario describes a penetration test for Sumace Consulting GmbH. The job application form is the new feature highlighted at kickoff, so it is a sensible area to inspect first—but this alone does not prove a vulnerability exists.

Phase 01

Map the feature

Document routes, form fields, uploads, redirects, responses and parameters affecting file selection.

Phase 02

Trace file handling

Look for paths influenced by filenames, templates, uploaded documents or stored applicant data.

Phase 03

Validate safely

Use minimal, non-destructive tests on the spawned HTB target and remain within scope.

Phase 04

Report & remediate

Record affected input, evidence, prerequisites, impact, reproducibility and recommended fix.

The supplied notes do not include a target IP, live responses or an answer key. A specific assessment vulnerability or answer cannot be confirmed from the text alone.

Revision checklist

Use this list to check your understanding before finishing the module.

  • I can distinguish LFI from RFI.
  • I understand how prefixes, suffixes and traversal affect resolved paths.
  • I can explain the difference between reading source code and executing included content.
  • I understand risks from PHP filters, uploads, session files and logs.
  • I can use fuzzing as a starting point and manually validate findings.
  • I can recommend allowlists, canonical path checks, least privilege and safe upload handling.
  • I can document scope, evidence, impact and remediation without overstating the result.
