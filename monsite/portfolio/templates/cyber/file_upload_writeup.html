File Upload Attacks

01

Scope and methodology

This write-up summarizes the supplied HTB Academy File Upload Attacks Skills Assessment article. The described target is an e-commerce-style site with a contact form that accepts an image attachment.

Authorized lab only. The target address, live responses, screenshots and flag were not provided for independent verification. Treat the chain below as the source article's reported walkthrough, not as a test result reproduced by this portfolio author. Add your own evidence after running the authorized Academy instance.

The investigation moves from normal upload behavior to extension discovery, then uses the permitted SVG format as a clue to investigate server-side XML processing. Source inspection explains how the upload is stored and validated.

02

Identify the upload attack surface

The Contact Us page contains a feedback form with a file attachment described as a screenshot. The article first uploads an ordinary image to establish the baseline, then compares responses while testing accepted extensions through an intercepting proxy.

Observation

Normal image accepted

Establish expected behavior before interpreting rejection messages or unusual responses.

Interesting result

SVG accepted

SVG is an XML-based image format. If processed unsafely, it can expose XML parser behavior beyond simple image rendering.

Directory fuzzing did not reveal the upload folder in the source article. That failure motivated the author to investigate whether SVG processing could disclose the upload handler's source code.

03

Why SVG processing matters

SVG files contain XML. XML parsers that allow unsafe external entity resolution may read local resources while processing attacker-controlled documents. This class of issue is known as XML External Entity (XXE).

Assessment concept: accepting an SVG is not automatically a vulnerability. The risk depends on how the server parses, sanitizes, transforms or renders it, and whether external entity resolution is enabled.

The article reports using an SVG-based XXE condition to disclose the PHP upload handler as encoded content, then decoding it to inspect the implementation. This write-up records the concept without claiming that the payload or response was independently reproduced here.

04

Source disclosure reveals storage behavior

The source article quotes the following storage logic from the handler:

CODE EXCERPT REPORTED IN THE SOURCE ARTICLE
$target_dir = "./user_feedback_submissions/";
$fileName = date('ymd') . '_' . basename($_FILES["uploadFile"]["name"]);
$target_file = $target_dir . $fileName;

The upload destination is user_feedback_submissions/. The server prepends a date string in yymmdd format to the original basename. According to the article, this makes the resulting filename predictable for that date.

Predictable naming is not sufficient by itself to cause code execution. It becomes relevant when combined with unsafe file validation, an exposed upload directory and a server configuration that interprets the uploaded file as executable code.

05

Understand each validation layer

The article identifies three checks in the upload handler: a PHP-extension blacklist, an image-extension allowlist expressed as a regular expression, and a MIME-type check.

LayerReported behaviorDesign concern
BlacklistRejects selected PHP-like extensions using a case-sensitive pattern.Blacklists tend to miss alternate or unexpected executable extensions.
Filename allowlistRequires the name to end in a short lowercase image-like extension.Extension syntax does not prove that a file is safe to store or serve.
MIME checkUses content-based type detection and expects an image MIME pattern.Content detection is useful but is not a substitute for safe storage and non-executable serving.

The source article's key observation is that different layers interpret the filename and content differently. A filename accepted by the application can still be dangerous if the web server applies a broader handler rule after storage.

Do not assume a MIME header supplied by the client is trustworthy. Conversely, server-side MIME detection alone cannot guarantee that uploaded content is harmless.
06

Application checks and Apache rules are separate

The article describes a server-side handler rule using a filename pattern that can match an executable-looking extension anywhere in the name rather than requiring it at the end.

ILLUSTRATIVE CONFIGURATION PATTERN DISCUSSED IN THE ARTICLE
<FilesMatch ".+\.ph(ar|p|tml)">
    SetHandler application/x-httpd-php
</FilesMatch>

The security issue is the mismatch between the application's end-anchored filename validation and a server handler pattern that is not end-anchored. Those rules operate at different layers and may disagree about whether a stored file should be treated as PHP.

Defensive priority: uploaded files should not be placed in a directory where the web server can execute them. Correct the server configuration and storage design rather than relying on a filename filter to compensate.
07

Content validation and metadata

The source article reports that simply prepending image magic bytes was not enough for the MIME check it encountered. It then describes placing a PHP payload in JPEG EXIF metadata so the file still resembles a valid JPEG to content detection while the server-side handler may interpret it differently.

EXIF is a metadata format commonly embedded in JPEG files. The broader lesson is that file formats can contain structured metadata and multiple types of content; a superficial check or one detection function should not be treated as a security boundary.

This page does not claim that the described sample was run against a live target here. In an authorized lab, record the accepted file type, server response and execution behavior separately so each claim is evidence-backed.

Impact and evidence checklist

If the full chain is confirmed in the authorized lab, the impact can extend beyond arbitrary file storage to server-side code execution under the web server's privileges.

  • Capture the baseline upload request and the normal successful response.
  • Record extension-testing results and distinguish rejection messages from acceptance.
  • Preserve a redacted source-disclosure excerpt showing the storage and validation logic.
  • Document the effective server handler configuration and why it differs from application validation.
  • Verify each link in the chain with reproducible evidence on your own spawned target.
  • Record the final impact only after direct confirmation; redact flags, secrets, tokens and unrelated user data from public screenshots.

10

Remediation and secure design

Fix the upload pipeline as a whole rather than trying to invent a perfect extension blacklist.

Use a strict allowlist

Permit only the business-required formats. Reject SVG if it is not needed, or sanitize and rasterize it in a constrained processing environment.

Validate content safely

Combine extension checks, server-side content inspection and format-specific parsing. Treat client-provided MIME values as untrusted.

Store outside web root

Use generated identifiers and private storage. Serve files through a controlled download handler with safe content headers.

Disable execution

Ensure upload directories cannot execute PHP or other server-side code. Remove broad handler rules and test the effective configuration.

Harden XML parsing

Disable external entity resolution and unnecessary network access when processing XML or SVG. Keep parsing libraries patched.

Apply least privilege

Run the web process with limited permissions, enforce size limits, log rejected uploads and monitor suspicious file-processing behavior.
