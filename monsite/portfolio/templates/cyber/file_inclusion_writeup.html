01

Scope & methodology

The supplied scenario describes Sumace Consulting GmbH, a fictional organization whose web application includes a recently added job application form. The assessment focuses on how request parameters and uploaded files are handled.

Authorized lab only. Run tests only against your spawned HTB Academy target. This page documents the supplied scenario; target IP, live responses and flag values are intentionally not fabricated. Add your own screenshots and verified results before claiming a completed practical run.

The methodology is to map the application, identify parameters that influence file operations, inspect source code where disclosure is possible, and determine whether separate weaknesses can be chained.

02

Reconnaissance: follow the file-handling features

The application exposes Home, Contact and Apply pages. The Apply page accepts applicant details, a resume and notes. Submission redirects to a thank-you page with a reflected first-name parameter.

OBSERVED ROUTE PATTERNS FROM THE SCENARIO
/thanks.php?n=<first_name>
/api/image.php?p=<image_reference>

The n parameter reflects text, but reflection alone is not evidence of LFI. The more promising candidate is the image endpoint's p parameter because it appears to influence a filesystem operation.

Testing note: use baseline requests and compare response content. Do not conclude that a parameter is vulnerable just because a traversal-looking string appears in the response.
03

Confirming a local file-read issue

The supplied walkthrough reports that fuzzing the image parameter revealed traversal behavior and access to a local system file. In your own lab, verify this with a harmless, readable test file and capture the response as evidence.

FUZZING TEMPLATE · REPLACE PLACEHOLDERS
ffuf -w /usr/share/seclists/Fuzzing/LFI/LFI-Jhaddix.txt:FUZZ \
  -u 'http://TARGET/api/image.php?p=FUZZ' \
  -fs RESPONSE_SIZE

Filter out known empty or baseline responses only after you understand normal behavior. Follow up promising results manually and record the exact request, status, response size and a short redacted excerpt.

A successful local file read is not automatically code execution. The next step is to understand which server-side function consumes the path.
04

Source-code disclosure explains the limitation

The source shown in the supplied scenario uses a string replacement and then calls file_get_contents().

VULNERABLE IMPLEMENTATION · FROM THE PROVIDED SCENARIO
<?php
if (isset($_GET["p"])) {
    $path = "../images/" . str_replace("../", "", $_GET["p"]);
    $contents = file_get_contents($path);
    header("Content-Type: image/jpeg");
    echo $contents;
}
?>

Two weaknesses stand out:

  • str_replace() is being used as a security filter instead of validating a permitted path.
  • file_get_contents() reads bytes; it does not execute PHP source contained in the file.

This explains why attempts to turn this specific endpoint into an execution primitive did not work in the described scenario. The file reader is still valuable because it can disclose source code and reveal other endpoints.

Key distinction: file read and file inclusion are different primitives. Identify the actual function and its behavior before choosing the next test.
05

Reviewing the upload handler

The provided application code derives a destination filename from the uploaded file's content hash and the submitted extension.

UPLOAD LOGIC · FROM THE PROVIDED SCENARIO
$tmp_name = $_FILES["file"]["tmp_name"];
$file_name = $_FILES["file"]["name"];
$ext = end((explode(".", $file_name)));
$target_file = "../uploads/" . md5_file($tmp_name) . "." . $ext;
move_uploaded_file($tmp_name, $target_file);
Finding A

No visible extension allowlist

The shown code takes an extension from the client filename but does not enforce a permitted set of document types.

Finding B

Content-derived filename

The MD5 digest makes the stored basename a deterministic function of the file bytes. This may help identify the destination, but is not a security control.

The dangerous condition is not hashing itself. It is storing untrusted content in a location that can later be reached by an execution-capable inclusion function, without sufficient file-type and execution controls.

06

Finding the second inclusion point

The supplied scenario reveals a region parameter in contact.php. The value is checked for dots and slashes before URL decoding, then concatenated into an include() path.

VALIDATION ORDER · FROM THE PROVIDED SCENARIO
if (str_contains($_GET["region"], ".") ||
    str_contains($_GET["region"], "/")) {
    $danger = true;
} else {
    $region = urldecode($_GET["region"]);
}

if (!$danger) {
    include "./regions/" . $region . ".php";
}

The flaw is a mismatch between the value being checked and the value later used. URL decoding changes the representation after validation. Security checks must apply to canonicalized input, and path containment must still be enforced.

General rule: validate after the relevant normalization step. Prefer mapping a short identifier to a fixed trusted file rather than accepting a path from the request.
07

How the weaknesses connect

The scenario's reported chain relies on three separate conditions being present at once.

StepWeaknessWhy it matters
1Local file readDiscloses PHP source and reveals application internals.
2Unsafe upload handlingMay allow attacker-controlled content to be stored with a dangerous extension.
3Unsafe include + validation-order bugMay cause stored content to be interpreted by PHP when included.

The central lesson is to keep testing across the application's feature boundaries. The endpoint that reveals source code does not necessarily execute it; source disclosure can reveal a different endpoint that has more dangerous behavior.

For your practical report, document each link separately and only claim a complete chain after each prerequisite has been verified on your own lab instance.

Impact and evidence

The provided walkthrough reports command execution and discovery of a flag in the lab. That is a reported outcome from the source material, not a result independently verified in this session.

  • Save the baseline request and response for the relevant endpoint.
  • Capture the file-read evidence with sensitive values redacted.
  • Document the source-code lines that establish the vulnerable data flow.
  • Record the upload validation behavior and where files are stored.
  • Demonstrate the inclusion validation flaw with a harmless controlled test before assessing impact.
  • Capture the final result only if reproduced in your own authorized instance; do not publish target credentials, tokens or live secrets.
Do not overstate the finding. Distinguish source-derived observations from tests you personally performed. Do not publish a fabricated flag or claim RCE without reproducible evidence.
09

Remediation

Fix the underlying design instead of adding more string filters.

Use fixed mappings

Accept a region or page identifier, then map it to a trusted server-side path. Never pass arbitrary request values to include().

Secure uploads

Use a strict allowlist, inspect file content, generate server-side names, set size limits and store files outside executable directories.

Enforce path containment

Canonicalize the path and verify that it remains inside the permitted directory. Reject unexpected paths.

Reduce impact

Run the application with least privilege, separate uploads from code, restrict secrets and disable unnecessary remote features.

SAFER DESIGN · FIXED IDENTIFIER MAP
<?php
$regions = [
    "AT" => __DIR__ . "/regions/AT.php",
    "DE" => __DIR__ . "/regions/DE.php",
];

$key = $_GET["region"] ?? "AT";

if (!isset($regions[$key])) {
    http_response_code(404);
    exit("Region not found");
}

include $regions[$key];
?>

This example demonstrates the allowlist principle. In production, also ensure that mapped files are trusted, permissions are restrictive and uploaded files cannot become executable through another route.

10

Lessons learned

This assessment is a useful example of chaining weaknesses rather than focusing on a single payload.

  • Reflection is not proof of file inclusion; trace input to a sensitive file operation.
  • Source disclosure helps explain behavior and can reveal additional vulnerable code paths.
  • Understand the difference between a file-reading API and an execution-capable inclusion.
  • Validation performed before decoding or canonicalization may protect the wrong representation.
  • Upload security depends on storage, validation and execution controls—not just filename generation.
  • Report the chain, its prerequisites, reproducible evidence and practical remediation.
